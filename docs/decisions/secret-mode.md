# 予定日の表示をユーザーごとに分ける（シークレットモード、奥さんの要望）

[← 目次（HANDOFF.md）](../../HANDOFF.md)

**背景：** 奥さんは、何をいつ作るかを川名さんに知られたくない（サプライズにしたい）。一方で、「明日はこれ、明後日はこれ」というスケジュール帳としては使いたい。

**仕様（2026-10-22 更新）**
2026-10-20 には「リストは2人とも見えて、日付だけ隠す」と決めていたが、よりシンプルな形に変えた（川名さん提案）。

| 項目 | 予定を見られる人（奥さん） | 予定を見られない人（川名さん） |
|---|---|---|
| 今週作るの画面 | 見える。川名さんのリクエストには「🙋 食べたい！」の印を付ける | **タブごと非表示** |
| レシピ一覧・詳細のボタン | 「＋ 今週作る」（今のまま） | **「🙋 食べたい！」**（押すと日付未定で今週作るに入る＝リクエスト） |
| 押した後の表示 | 「✓ 今週作る」 | 「✓ リクエスト済み」（**自分が押したものだけ**。奥さんが入れたものは出さない） |
| 「作った！」 | 押せる（今週作るの画面にあるため） | 押せない（画面がないため） |
| メモの買い物リスト | 材料の下に料理名を出す | **料理名を出さない** |
| 設定の切り替え | 本人が自分の設定画面で切り替える（信頼ベース。開発者に操作権限がないのは意味不明、笑） | 同左 |

- 「誰が入れたか」は `todo_items.added_by` にすでにあるので、テーブルの変更は不要。ユーザーごとの設定（今週作るを表示するか）を置く場所だけ足す（例：`profiles` テーブル）
- ボタンの表記は、見られる人と見られない人で変える案。2人とも「食べたい！」にする案もあり、作るときに決める
- **隠すのは画面だけ**でよい。買い物リストの材料そのものから料理が推測できる可能性は残るが、**ネタバレに神経質にならなくてよい**（川名さん判断、2026-10-22）。データを DB 側で隠す仕組みは作らない

**表記の変更（2026-10-22）**
- 「今週作る」の名前を、タブ・画面の見出し・ボタン・メモ画面ですべて **「リクエスト」**（アイコン 🙋）に変更した（川名さん指定）。中身（カレンダー・予定日・作った！）はそのまま
- ボタン：奥さん側は「＋ リクエスト」→「✓ リクエスト済み」、シークレットモード側は「🙋 食べたい！」→「✓ リクエスト済み」
- 内部の名前（`todo`、`/todo`、`TodoItem` など）は変えていない
- ※ 途中で「シークレットモードの人には自分のリクエストだけの画面を出す」案も作ったが、**シンプルに表記を変えるだけでよい**（川名さん判断）として戻した

**「食べたい！」の仕組み（2026-10-22 実装）**
- シークレットモードの人が「🙋 食べたい！」を押すと、日付未定でリクエストに入り、「リクエストで入った」印（`TodoItem.requested`）が付く
- **同じ料理がすでに日付未定で入っていたら、増やさずにその1件に印を付ける**（奥さんが入れた料理に後から「食べたい！」するケース）
- シークレットモードの人の「✓ リクエスト済み」は、自分が押したもの（印のあるもの）だけ。奥さんが入れた料理は表示しない
- 奥さんのリクエスト画面では、印のある料理に「🙋 食べたい！」を表示する
- シークレットモードのときは、メモの買い物リストで材料の下に料理名を出さない
- **DB につなぐとき：** 今のスキーマの `todo_items.added_by`（追加した人）だけでは「誰がリクエストしたか」を表せない（奥さんが入れた料理に後から印を付けるため）。`todo_items` に `requested_by`（リクエストした人、null なら印なし）を足すマイグレーションが必要

**実装の状況（2026-10-22）**
- 設定画面に **「シークレットモード」**（川名さんの命名）のスイッチを追加。オンにすると「リクエスト」のタブが消え、`/todo` を直接開いてもレシピ一覧に移る
- 「🙋 食べたい！」まわり（上記）も実装済み
- シークレットモードの値は、今はモックのデータ置き場（メモリ上）にあり、**リロードでオフに戻る**。DB への差し替えのときに、ユーザーごとの設定として保存する
