# DB（命名規則・スキーマ・Supabase の構築・DB とのつなぎ方）

## DB の命名規則（2026-10-17 決定）

| 対象 | ルール | 例 |
|---|---|---|
| テーブル | **複数形の snake_case、接尾辞なし** | `recipes`, `cook_logs`, `recipe_ingredients` |
| ビュー（作る場合） | `_view` を付けてテーブルと区別する | `recipe_summary_view` |
| 列 | snake_case。外部キーは `<単数形>_id` | `recipe_id`, `created_by` |
| 日時 / 日付 | 日時は `_at`（timestamptz）、日付は `_on`（date） | `created_at`, `cooked_on` |

**理由：** PostgreSQL / Supabase で一般的な書き方で、supabase-js でも `from('recipes')` と自然に読める。
SSAM は前半が `xxx_table`、後半が接尾辞なしで混在してしまったので、今回は最初に決めて統一する。

### DB 関数（複数の書き込みを1トランザクションにまとめたもの）
| 関数 | 中身 | 理由 |
|---|---|---|
| `save_recipe()` | レシピの追加・編集。材料と手順は全部消して入れ直す | 3テーブルにまたがる。フロントから分けて書くと、途中で失敗したとき中途半端なデータが残る |
| `mark_cooked()` | 今週作るから外して履歴に追加。日付は「予定日が今日以前なら予定日、未来・未定なら今日」 | 削除と追加の片方だけ成功するのを防ぐ |
| `add_todo_ingredients_to_shopping()` | 今週作るの材料を買い物リストへ（重複は入れない） | 集計と追加を DB 側で一度に行う |
| `request_recipe()` | 「食べたい！」：同じ料理の日付未定があれば印を付ける、なければ印付きで追加（#18） | 「探す → 追加か更新」を2回に分けると、2人が同時に押したときにずれるため |

どれも `security invoker`（呼んだ人の権限で動き、RLS がそのまま効く）と `set search_path = ''`（同名の偽テーブル・関数へのすり替えを防ぐ）を付けている。

### 主な判断
| 判断 | 理由 |
|---|---|
| レシピは**論理削除**（`deleted_at`）。履歴があるレシピは物理削除できない（外部キー `restrict`） | 作ったご飯の履歴を残すため |
| 材料・手順は別テーブル、タグは `text[]`（GIN インデックス） | 材料はあとで「材料から検索」ができるように。タグはただのラベル |
| 作った日の既定値は**日本時間**（`now() at time zone 'Asia/Tokyo'`） | DB は UTC なので、`current_date` だと朝9時前に記録すると前日になる |
| **DB のタイムゾーンは UTC のまま**（日時の列 `created_at` などは `+00` で表示される）。日付の列（`cooked_on`・`planned_on`）だけ日本時間で持つ（2026-10-24 川名さんと確認） | `timestamptz` は「ある一瞬」を持つだけで、`+00` は表示の都合。保存は UTC・表示で直すのが定石で、DB の設定を変えると `current_date` の意味も変わる。アプリの画面には日時を出していない。日本時間で見たいときは SQL で `at time zone 'Asia/Tokyo'` |
| **お気に入りは夫婦共通**（`recipes.is_favorite`） | 当初は人ごと（`recipe_favorites` テーブル）で設計したが、モックを触ったうえで川名さんが夫婦共通を選んだ（2026-10-18）。どちらかが付ければ2人ともお気に入り |
| 共有メモは1行固定（`check (id = 1)`、RLS で更新のみ許可） | 冷蔵庫のホワイトボードのような1枚のメモ |
| 作成者・作成日時・更新日時を各テーブルに持つ（`created_by` の既定値は `auth.uid()`、`updated_at` はトリガーで自動更新） | 画面には出ないが、誰がいつ変えたか追えるように |

### 権限（GRANT）：Supabase の仕様変更への対応（2026-10-18）
- **2026-05-30 以降に作った Supabase プロジェクトでは、`public` のテーブルに権限が自動で付かない**（既存プロジェクトも 2026-10-30 から同じ扱い）。テーブルごとに `GRANT` を明示的に書く必要がある。付けないと supabase-js から一切読めない
  - 出典：[Supabase 公式 changelog](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)
- 対応：マイグレーションに `GRANT` を追加
  - `authenticated`（ログイン済み）と `service_role`（サーバー側）に、各テーブルの select / insert / update / delete
  - 共有メモは `authenticated` に select / update だけ
  - `anon`（未ログイン）には何も付けない
  - DB 関数は PostgreSQL の既定で誰でも実行できるので、`public` と `anon` から実行権限を外し、`authenticated` と `service_role` にだけ付ける
- **GRANT（そのテーブルに触れるか）と RLS（どの行に触れるか）の二段構え**にしている
- プロジェクト作成時の「Automatically expose new tables」は**外したまま**にする（明示的な GRANT で足りる。外す方が安全）

### RLS（行レベルセキュリティ）
- 未ログイン（`anon`）は何もできない
- ログイン済み（`authenticated`）は全データを読み書きできる（利用者は夫婦2人だけで、新規登録は閉じるため）
- 共有メモだけは読み取りと更新のみ（行の追加・削除は不可）

### 検証の方法と限界
- Docker の PostgreSQL 17 にマイグレーションを流し、テスト SQL で各機能・制約・RLS を確認した
- **2026-10-24〜 テストはリポジトリに入っている**（`supabase/tests/`、実行は `bash supabase/tests/run.sh`）。詳しくは [dev-process.md](dev-process.md)
- `auth.users` / `auth.uid()` / `anon` / `authenticated` ロールは**検証用の代用品**。本物の Supabase とは同じではない
- 権限については、新しい Supabase を再現した検証（テーブルへの自動 GRANT なし）でも確認した。未ログインはテーブル・関数とも権限の段階で拒否されることを確認済み
- **本物の Supabase に流すときに、もう一度確認すること**：`auth.uid()` の動作、RLS の効き方、Security Advisor の警告

### #18 で追加したもの（2026-10-24、マイグレーション `20261024023439_add_requests_and_user_settings.sql`）
| 判断 | 理由 |
|---|---|
| 「食べたい！」は `request_recipe()` 関数にした | 日付未定の同じ料理は1つまで（一意制約）なので、「あれば印を付ける・なければ追加」を1つのトランザクションでやる必要がある |
| 日付が決まった後の「食べたい！」は、日付未定の行を新しく足す | 奥さんの予定（日付）を動かさないため |
| 設定は `user_settings`（`profiles` ではなく） | 命名規則（複数形の snake_case）に合わせ、中身が分かる名前に |
| `user_settings` の行は、設定を初めて変えたときに作る（行がなければ既定値） | `auth` スキーマにトリガーを足す方法もあるが、Supabase の内部に手を入れるので避けた |
| `user_settings` の RLS は**自分の行だけ**、削除は GRANT しない | 相手の設定は見えない・変えられない。設定を消す必要はない |
| `set_updated_at` の実行権限を `public`・`anon`・`authenticated` から外した | トリガー専用で、直接呼ぶ必要がない。トリガーとしての動作には影響しない（テストで確認） |

### #13 レシピの削除（2026-11-20、マイグレーション `20261120115825_delete_recipe.sql`）
| 判断 | 理由 |
|---|---|
| 論理削除（`deleted_at`）。行は消さない | 作ったご飯の記録（`cook_logs`）がレシピを参照している（`restrict`）。記録には料理名を「（削除済み）」付きで出し続ける |
| 削除とリクエストから外すのを、1つの関数 `delete_recipe()` にまとめた | フロントから2回に分けると、片方だけ成功することがある |
| 買い物リストの品物は残す | レシピを消しても、その材料は買う必要があるかもしれない。料理名は一覧にあるレシピからしか引かないので、削除後は出なくなる |
| 写真（Storage）は消さない | 削除したレシピの写真は、どの画面にも出ない（写真の URL は一覧にあるレシピの分しか取らない）。それでも残すのは、間違えて消したときに `deleted_at` を null に戻せば写真ごと元に戻せるため。1枚が小さく、無料枠の容量を圧迫しない |
| `request_recipe()` で、削除済みのレシピを受け付けない（`for share` で押さえてから確かめる） | もう1台で古い画面のまま「食べたい！」を押されたときに、消えたレシピがリクエストに入らないように。`for share` がないと、確かめた直後に削除される隙間が残る |
| 削除のボタンは、編集画面ではなく**詳細の上の帯**（「編集」の左）に置いた | Issue の最初の案は編集画面の一番下だった。詳細に置くと、削除後に履歴を置き換えれば「戻る」で「見つかりません」が出ない（編集画面からだと、一覧 → 詳細 → 編集の「詳細」が残る）。帯は料理中に触る手順・「作った！」から離れていて、押し間違えにくい。よく押す「編集」は右端のまま |
| 削除の後の読み直しは待たない（`useDeleteRecipe` の `onSuccess` で Promise を返さない） | 待つと、読み直しが先に終わった瞬間に、開いている詳細が「レシピが見つかりません」に変わる |
| 確認は `window.confirm`（自作のモーダルにしない） | ほかの確認と揃える。見慣れた標準の形の方が、大事な確認で誤操作が少ない |

**受け入れたリスク**：詳細の「＋」（`useAddTodo`）は `todo_items` に直接 insert するので、削除とまったく同じ瞬間に押されると、消えたレシピのリクエストが1件残りうる。2人で使うので起きる見込みはほぼなく、残ってもリクエストの画面には出ない（一覧にないレシピは出さない）。ただ、「材料から追加」（`add_todo_ingredients_to_shopping`）では、その材料が買い物リストに入る

## Supabase の構築（2026-10-18）

### プロジェクト
| 項目 | 内容 |
|---|---|
| プロジェクト名 | WhatsEat |
| リージョン | **Northeast Asia (Tokyo)**（`ap-northeast-1`） |
| PostgreSQL | 17 |
| 「Automatically expose new tables」 | 外したまま（権限はマイグレーションの GRANT で明示的に付ける） |

**リージョンの注意：** 最初は誤って `ap-south-1`（ムンバイ）で作ってしまい、DB が空のうちに削除して作り直した。リージョンは**作成後に変えられない**。リストの中で `ap-northeast-1` を選ぶこと。

### Supabase CLI
- **npm の devDependency として入れている**（`supabase` 2.121.0）。実行は `npx supabase ...`
- 理由：Homebrew（`brew install supabase/tap/supabase`）で入れようとしたところ、Mac の Command Line Tools が macOS 27 に対応しておらず失敗した。npm 版は Mac 用の実行ファイルが直接入るので Command Line Tools を使わない。バージョンが `package.json` に残り、別の PC でも `npm install` でそろう利点もある
- Command Line Tools の更新は、Supabase とは関係なく Mac のメンテナンスとして別途やっておくとよい
- `supabase init` で作った `supabase/config.toml` はローカル開発用の設定。本番の設定（認証など）には自動では反映されない

### マイグレーションの反映手順
```bash
npx supabase login            # 初回のみ（ブラウザで認証）
npx supabase link             # 初回のみ（プロジェクトを選び、DB のパスワードを入力）
npx supabase db push --dry-run   # 何が反映されるか確認（DB は変更しない）
npx supabase db push             # 反映
npx supabase migration list      # ローカルと Supabase の適用状況を比べる
```
- **コミット済みのマイグレーションだけを流す**（git の履歴と DB の中身をずらさないため）
- Supabase のダッシュボードで直接スキーマを変えない（`db push` が同期エラーになる。変更は必ずマイグレーションで）
- 新しいマイグレーションは `npx supabase migration new <名前>` で作る（日時付きのファイル名になる）

### 反映後の確認（2026-10-18、`npx supabase db query --linked` と `db advisors` で確認）
- テーブル7つすべて作成済み、RLS もすべて有効、ポリシー8つ、共有メモの初期行あり
- 未ログイン（anon）は読み書き不可、DB 関数も実行不可
- **Security Advisor：0件**
- Performance Advisor：INFO が11件。今は対応しない
  - 作成者の列（`created_by` など）の外部キーにインデックスがない（6件）：その列で検索しない。利用者は2人なので影響なし
  - インデックスが未使用（5件）：DB が空で一度も検索していないため

### 不要な権限の整理（2つ目のマイグレーション）
- 初期スキーマを流した後、`anon` と `authenticated` に **TRUNCATE / REFERENCES / TRIGGER / MAINTAIN** が付いていることに気づいた。自分で付けたものではなく、Supabase の `postgres` ロールの既定値（`pg_default_acl` で `anon=Dxtm` を確認）から来ていた
  - TRUNCATE は **RLS を無視して全行を消せる**。Data API は TRUNCATE に対応していないのでアプリ経由で悪用される心配は低いが、使わない権限は外しておく
  - MAINTAIN は PostgreSQL 17 で追加された権限（LOCK TABLE、VACUUM など）
- `20261018115231_revoke_unused_table_privileges.sql` で、今あるテーブルから外し、今後作るテーブルにも付かないよう既定値を変えた（`service_role` は対象外）
- Docker の PostgreSQL で Supabase と同じ既定値を再現して検証済み：外れること、今後のテーブルにも付かないこと、アプリの操作が壊れないこと

### 認証の設定（2026-10-20）
| 項目 | 内容 |
|---|---|
| ユーザーの作り方 | **ダッシュボードから作る**（Authentication → Users → Add user → Create new user。「Auto Confirm User」をオンにして、確認メールなしでログインできる状態にする） |
| 作成済み | 川名さんのアカウント（2026-10-20、メール確認済み） |
| 奥さんのアカウント | **作成済み（2026-10-24、#31）**。ダッシュボードで Auto Confirm をオンにして作成。パスワードは川名さんが決めて直接伝える。**アプリにパスワード変更の機能は作らない**（ログインは期限なしで続き、最初の1回だけ入力する。変えたいときは川名さんがダッシュボードの Users から変える。機能が欲しくなったら Issue（中）） |
| 新規登録 | **閉じた**（Authentication → Sign In / Providers → 「Allow new users to sign up」をオフ） |
| アプリからのユーザー作成 | **作らない**。ユーザー作成には管理者用キー（service_role）が必要で、フロントには置けないため。2人分なのでダッシュボードで十分 |

**新規登録を閉じた理由（重要）：** 今の RLS は「ログイン済みなら全データを読み書きできる」で、これは**アカウントが夫婦の2つしか存在しない**ことが前提。アプリの URL と公開用キーはフロントの JavaScript に入るので誰でも見られ、新規登録が開いていると、それを使って誰でもアカウントを作れてしまう（＝ログイン済みになり、全データが見える）。**フロントを DB につなぐ前に閉じておくことが必須。**

**確認方法：** 公開用キーで `POST /auth/v1/signup` を送り、**HTTP 422 `signup_disabled`**（Signups not allowed for this instance）が返ること、ユーザー数が増えていないことを確認した（2026-10-20）。

| iPhone の注意 | Safari とホーム画面のアプリでログイン状態が共有されない | ホーム画面に追加したら、アプリ側で一度ログインが必要 |
| エラーメッセージ | 「メールアドレスかパスワードが違います」のように、どちらが違うかは言わない | 推測されにくくするため |

## DB とのつなぎ方（#3、2026-10-24 決定）

### 採用：TanStack Query（旧 React Query）
モックの `MockStoreProvider`（1つの大きな Context）を Supabase 版に書き換えるのではなく、**TanStack Query** で DB のデータを扱う。

| 理由 | 中身 |
|---|---|
| 読み込み中・エラーを自分で持たなくてよい | `isPending`・`error`・`refetch` をライブラリが持つ。画面ごとに useState を書かない |
| **#23（アプリに戻ったときの読み直し）がほぼ標準で入る** | `refetchOnWindowFocus`：画面が表示に戻ったら、古くなったデータを読み直す。ホーム画面から開いた PWA で実際に効くかは、#4 の後に iPhone で確認する（まだ確認していない） |
| 画面ごとに少しずつ差し替えられる | 使う画面だけ `useRecipes()` などに替える。差し替えが終わるまで、ほかの画面はモックのまま動く |
| 現場での使われ方 | React でサーバーのデータを扱うときの定番のひとつ |

不採用：Context を Supabase 版に書き換える（B）。小さいアプリなら成り立つが、読み込み中・エラー・読み直しを全部自分で書くことになり、一度に全画面を替える形になりがちなため。

### 置き場所と決まりごと
| もの | 場所 | 中身 |
|---|---|---|
| 設定 | `src/utils/queryClient.ts` | `staleTime` 30秒（画面を行き来するたびには読まない）、`retry` 1回、`refetchOnWindowFocus` |
| DB の型 | `src/types/database.ts` | **自動生成。手で直さない**。マイグレーションを本番に反映したら `npm run gen:types` で作り直す（`--linked` で本番のスキーマから作る） |
| テーブルごとの読み書き | `src/api/〇〇.ts`（#4 から） | DB を読む関数と、**DB の行（snake_case）→ 画面の型（camelCase）の変換**をここに置く。画面は今の型（`Recipe` など）のまま使える |
| 読み込み中 | `components/common/Loading.tsx` | |
| 読み込みの失敗 | `components/common/LoadError.tsx` | 「読み込めませんでした」＋もう一度読み込むボタン（`refetch` を渡す） |
| 保存の失敗 | トーストの `error` | 文言は `utils/dbError.ts` の `dbErrorMessage()`。SQLSTATE（`23505` など）と通信エラーを日本語にする。DB 関数の `raise` の文言には id が入るので、そのままは出さない |

- `createClient<Database>`：Supabase のクライアントに DB の型を渡し、列名の打ち間違いをビルドで気づけるようにした
- **ログアウトしたら `queryClient.clear()`**（AuthProvider の `SIGNED_OUT`）。同じ端末で別の人がログインしたときに、前の人のデータ（設定など）を見せないため
- キャッシュはメモリ上だけ。**ローカルストレージには保存しない**（CLAUDE.md「サーバーを正」）

### アプリに戻ったときの読み直し（#23、2026-10-24 決定）
ホーム画面から開いた PWA には「再読み込み」ボタンがないので、相手の変更を見る手段が要る。

| 案 | 判断 | 理由 |
|---|---|---|
| アプリに戻ったときに読み直す | **採用** | TanStack Query が `visibilitychange` を見ている（`query-core` の `focusManager` で確認）。iPhone でアプリを切り替えて戻ると発生する。`staleTime` の30秒を過ぎたデータだけ読み直す |
| 下に引っ張って更新 | 今はやらない | 上で足りる見込み。iOS の PWA で自前で作るとスクロールとぶつかりやすい。足りなければ Issue（中）にする |
| Realtime | #12（通知）と一緒に検討 | 2人が同時に同じ画面を見る場面は少ない |

**実機で確認済み（2026-10-24）**：プレビューをホーム画面に追加した iPhone でレシピ一覧を開いたまま別のアプリへ → Mac で★を変更 → 30秒以上たってから戻ると、★が変わっていた。

### レシピを DB につないだ（#4、2026-10-24）
- `src/api/recipes.ts`：材料・手順を `recipes` にぶら下げて**1回の問い合わせ**で読む（PostgREST の結合）。結合した側の並び順は保証されないので、`position` で並べ直す。行の型は `QueryData` で select の文字列から推論させる
- `src/hooks/useRecipes.ts`：一覧と詳細は**同じ queryKey（`['recipes']`）**を使い、詳細は `select` で1件を取り出す。一覧から開いたときに読み込みを待たない
- **お気に入りは楽観的更新**（タップした瞬間に★を変え、失敗したら戻してトースト）。返事を待つと★の反応が遅れるため。ひとことメモは保存が終わってから閉じる（失敗したら書いた内容を残す）
- 作った回数・最後に作った日は `cook_logs` から、そのレシピの分だけ読む

### レシピの追加・編集を DB に保存した（#5、2026-10-24）
- 保存は DB 関数 `save_recipe()` を `supabase.rpc()` で呼ぶ（3テーブルを1トランザクション）
- **保存 → 一覧の読み直しが終わってから詳細画面へ移る**（`onSuccess` で `invalidateQueries` の Promise を返す）。待たずに移ると、追加したばかりのレシピがまだ手元になく「見つかりません」が一瞬出るため
- 保存中はボタンを押せなくする（二重保存の防止）。失敗したらトーストを出し、入力内容は残す
- **`save_recipe` の引数の型は `api/recipes.ts` に自分で書いた**（`SaveRecipeArgs`）。型の生成では関数の引数が null を受け付けるか分からず、すべて null 不可になるため。rpc を呼ぶところで1回だけ `as` で当てはめる。`database.ts` は生成し直すと上書きされるので手で直さない
- DB の check 制約（料理名100文字まで、調理時間・何人分は1以上）に合わせて、入力欄に `maxLength`・`min` を付けた。それでも違反したら `23514` →「入力内容を確認してください」

### リクエストを DB につないだ（#6、2026-10-24）
- `src/api/todo.ts`・`src/hooks/useTodo.ts`。「作った！」は `mark_cooked()`、「食べたい！」は `request_recipe()` を rpc で呼ぶ
- 型 `TodoItem` の `requested`（true/false）を **`requestedBy`（押した人の id）** に変えた（DB の `requested_by` に合わせる）。シークレットモードの「リクエスト済み」は `requestedBy === 自分の id` で判定
- 保存が終わってから表示を変える（楽観的更新はしない）。予定日を変えるとカードが別の欄に移るため、失敗時に戻す処理が複雑になる
- 予定日の重複（`23505`）だけはトーストではなく、画面の中に「その日にはすでに同じレシピが入っています」と出す（エラーの扱いを呼び出す側に任せる）
- 「作った！」の後は、リクエストと「作った日」（`['cookedDates']` で始まる名札すべて）を読み直す
- **仕様の変更（川名さんと決定）：** 一覧・詳細のボタンは、**リクエストに入っていれば日付があってもなくても「✓ リクエスト済み」**。「作った！」か ✕ で外れたら「＋ リクエスト」に戻る。これまでは日付未定のときだけ「済み」で、日付を決めると別の日にもう一度入れられるよう戻っていたが、入っているのに入っていないように見えるため変えた。一覧から同じ料理を別の日に入れることはできなくなった（DB の一意制約はそのまま）。日付から料理を選ぶ機能は #29
- 名前のずれ：画面は「リクエスト」だが、テーブル・型・フォルダ・URL は「今週作る」の頃の `todo` のまま（表記だけ変えた経緯、[ui.md](ui.md)）。揃えるならマイグレーション・関数・RLS・テストまで変わるので、今はやらない

### メモ画面（買い物リスト・共有メモ）を DB につないだ（#7、2026-10-24）
- `src/api/shopping.ts`・`src/hooks/useShopping.ts`。「リクエストの材料から追加」は `add_todo_ingredients_to_shopping()` を rpc で呼び、追加件数を出す
- **チェック（買った）は楽観的更新**。お店で次々に付けるので、1つずつ返事を待つともたつくため。ほかの操作は保存が終わってから表示を変える
- **共有メモは、打ち終わって1秒後に保存（デバウンス）＋入力欄から離れたとき（blur）にも保存**。書いている間は手元の「書きかけ（draft）」を出し、アプリに戻ったときの読み直し（#23）で DB の本文が変わっても入力欄を上書きしない。保存が成功したら、読み直さずに保存した本文を置き場に入れる（古い本文が一瞬出ないように）
- 2人が同時に書いたら後から保存した方が残る（同時に同じメモを書く場面は少ないので、対策はしない）
- メモ画面は「買い物リスト」「共有メモ」の2つの部品に分け、それぞれが自分の読み込み中・エラーを出す

### 作ったご飯（履歴）を DB につないだ（#8、2026-10-24）
- `src/api/history.ts`・`src/hooks/useHistory.ts`。`cook_logs` に**レシピの名前・タグを結合して1回で読む**（`cooked_on` の新しい順、同じ日は後から記録した方が上）。レシピ一覧のデータは論理削除したものを含まないので、そこから探すと削除したレシピの名前が出せないため
- 削除されたレシピは、Issue の「（削除されたレシピ）と出す」から少し変えて、**名前に「（削除済み）」を添え、詳細画面へのリンクを外す**（名前が分かる方が振り返りやすい）。レシピの削除機能（#13）ができるまでは起きない
- 「作った！」の後の読み直しに、履歴（`['history']`）も入れた
- 作った回ごとのメモ（`cook_logs.memo`）は、あれば出すだけ。記録する機能は #25

### シークレットモードを DB に保存した（#9、2026-10-24）
- `src/api/settings.ts`・`src/hooks/useSettings.ts`。自分の行を `maybeSingle()` で読み、なければオフ。切り替えは `upsert`（`onConflict: user_id`）で、スイッチは楽観的更新
- **MainLayout が設定を読み終わるまで、タブも画面も出さない**。読み込み中をオフとして扱うと、開いた一瞬だけ「リクエスト」タブや相手の予定が見えてしまい、シークレットモードの目的に反するため。各画面は `useSecretMode()`（true / false）を使うだけでよい
- 設定は人ごと（RLS で自分の行だけ）。同じ人なら端末をまたいで同じになる

**途中の状態（#4〜#9 の間、develop のみ）：** レシピだけ DB、リクエスト・履歴・追加フォーム・シークレットモードはモックのまま。一覧の「＋ リクエスト」やフォームの追加は、DB のレシピとはつながらない。**本番がこの状態にならないよう、main へのマージは #4〜#9 がそろってからまとめて行う**（#18 のように Issue ごとの PR にはしない）

**確認用のデータ：（2026-10-24 #32 の前に全部削除済み。#33 のコメント参照）** 確認で入れたリクエスト（`todo_items`）・作った記録（`cook_logs`）も含めて、**奥さんに渡す前に全部消す**（`cook_logs` が参照しているレシピは物理削除できないので、`cook_logs` → `todo_items` → レシピの順に消す）。最初に入れたのは、モックのレシピ6品を、作った人＝川名さんとして本番の DB に入れた（2026-10-24、`save_recipe` を authenticated・川名さんの uid で実行）。**奥さんに渡す前に消す**（残したいものは残す）。※ 1つの SQL 文の中で `save_recipe` が入れた行は、同じ文の外側の update からは見えない（同じスナップショット）ので、お気に入り・メモは別の文で入れた
